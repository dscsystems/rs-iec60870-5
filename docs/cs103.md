# `cs103` — IEC 60870-5-103 master for protection equipment

The `cs103` module implements the **primary station (master)** side of
IEC 60870-5-103, the companion standard for the informative interface of
protection equipment.

The link layer is the same FT1.2 unbalanced procedure as
[`cs101`](cs101.md) — the module reuses its frame codec and transports — while
the application layer is 103-specific:

```text
ASDU = | type ID | VSQ | cause | common address | FUN | INF | elements... |
bytes |    1    |  1  |   1   |       1        |  1  |  1  |      n      |
```

Key differences from 101 and 104:

* Every identifier field is **one octet**; there is no `asdu::Params` for the
  two ends to agree on.
* Information objects are addressed by **function type** (FUN) and
  **information number** (INF) instead of an information object address.
* Events carry the 4-octet **CP32Time2a** tag, whose date comes from the local
  clock; time synchronization uses CP56Time2a.
* Measurands are signed **13-bit** values with OV and ER flags.
* The link address and the ASDU common address are conventionally equal, and
  this module uses one address per device for both.

## Usage

```rust,no_run
use rs_iec60870_5::cs103::{
    Asdu, Client, ClientHandler, ClientOption, Config, Dco, Link, MeasurandsInfo,
    SerialConfig, TimeTaggedInfo, fun, inf,
};

struct Relays;

#[async_trait::async_trait]
impl ClientHandler for Relays {
    async fn time_tagged(
        &self,
        _link: &dyn Link,
        pack: &Asdu,
        info: TimeTaggedInfo,
    ) -> rs_iec60870_5::Result<()> {
        println!("device {} FUN={} INF={} {}", pack.common_addr, info.fun, info.inf, info.dpi);
        Ok(())
    }

    async fn measurands(
        &self,
        _link: &dyn Link,
        _pack: &Asdu,
        info: MeasurandsInfo,
    ) -> rs_iec60870_5::Result<()> {
        for m in &info.values {
            println!("  {:.4} of full scale", m.f64());
        }
        Ok(())
    }
}

# #[tokio::main]
# async fn main() -> rs_iec60870_5::Result<()> {
let mut cfg = Config::new();
cfg.serial = SerialConfig::new("/dev/ttyUSB0", 9600);   // 8E1 by default
cfg.link_address = 3;                                   // the relay's address

let cli = Client::new(Relays, ClientOption::new().with_config(cfg)?);
cli.start()?;
cli.wait_link_active().await;

cli.general_command(3, fun::OVERCURRENT_PROTECTION, inf::LED_RESET, Dco::On, 42)
# }
```

Multi-drop: add each relay with `ClientOption::with_secondary_address(addr)`.
TCP encapsulation works exactly as in cs101 — set `Config::transport` and
`Config::tcp`.

## What the client does by itself

1. **Link initialization**: request status of link, then reset of the
   communication unit. The device then reports its **identification message**
   (ASDU 5), which the client collects with a class 1 poll — the device sets
   ACD on its reset acknowledgement — and delivers to `identification`.
2. With `Config::auto_init` (the default), every newly active device gets a
   **time synchronization** (ASDU 6) followed by a **general interrogation**
   (ASDU 7), in that order.
3. **Continuous class 2 polling** collects cyclic measurands; a set ACD bit
   switches to class 1 to fetch pending events.

FCB tracking, duplicate suppression, t₁/t₂ repetition and multi-drop
round-robin work as in cs101.

## Requests and commands

Everything is queued and transmitted when the target device's link is free.
The [`Link`] trait carries the application-level actions and is what handlers
receive; [`Client`] implements it.

```rust,no_run
# use rs_iec60870_5::cs103::{Asdu, Client, ClientHandler, Dco, Link, fun, inf};
# struct H; impl ClientHandler for H {}
# fn f(cli: &Client<H>) -> rs_iec60870_5::Result<()> {
cli.time_sync(3)?;                       // ASDU 6, with the current time
cli.general_interrogation(3, 1)?;        // ASDU 7, scan number 1
cli.general_command(3, fun::OVERCURRENT_PROTECTION, inf::AUTO_RECLOSER_ACTIVE, Dco::On, 42)?;

// Link-layer actions, rarely needed since the client runs the procedure.
cli.send_reset_cu(3)?;                   // FC 0, reset of the communication unit
cli.send_reset_fcb(3)?;                  // FC 7, the 103-specific lightweight reset
cli.send_request_link_status(3)?;
cli.send_req_data_class2(3)?;

// A hand-built or private ASDU.
cli.send_to(Asdu::general_interrogation(3, 2), 3)?;
# Ok(())
# }
```

`send(asdu)` targets the default device — the first configured address, or
`Config::link_address`.

**Command acknowledgements** return as **ASDU 1 with cause 20** (positive) or
**21** (negative), delivered to `time_tagged`, whose `info.sin` carries the RII
of the original command. That is how a reply is matched to the command that
caused it.

## `ClientHandler`

The device that produced an ASDU is identified by `pack.common_addr`. Every
method has a default that does nothing.

| Type | Method |
|------|--------|
| 1, 2 | `time_tagged(link, pack, info)` — events, interrogation replies, command acknowledgements |
| 3, 9 | `measurands(link, pack, info)` |
| 5 | `identification(link, pack, info)` |
| 8 | `gi_termination(link, pack, scn)` |
| other | `asdu(link, pack)` — ASDU 4, 6, generic and disturbance types |
| every | `asdu_all(link, pack)`, before routing |

Plus `on_connect(link)`, `on_device_active(link, addr)` and
`on_connection_lost(link)`. With `auto_init`, the time synchronization and
interrogation are already queued by the time `on_device_active` runs.

An ASDU 1 means different things depending on its cause: `Cause::SPONTANEOUS`
is an event, `Cause::GI` an interrogation reply, `Cause::COMMAND_ACK_POS` or
`COMMAND_ACK_NEG` a command result, and `Cause::RESET_CU`,
`Cause::START_RESTART` or `Cause::POWER_ON` a device restart.

## Application layer

`Asdu` is the 103 message. Constructors for the control direction:

```rust
# use rs_iec60870_5::cs103::{Asdu, Dco, fun, inf};
let a = Asdu::time_sync(3, chrono::Utc::now());
let a = Asdu::general_interrogation(3, 7);
let a = Asdu::general_command(3, fun::OVERCURRENT_PROTECTION, inf::LED_RESET, Dco::On, 42);
# assert_eq!(a.get_general_command().unwrap().rii, 42);
```

Getters, each returning `Result` and never panicking: `get_time_tagged`
(ASDU 1 and 2), `get_measurands` (3 and 9), `get_time_tagged_measurands` (4,
the short-circuit location), `get_identification` (5), `get_time_sync` (6),
`get_general_interrogation` (7), `get_gi_termination` (8),
`get_general_command` (20). `marshal_binary` and `unmarshal_binary` handle the
wire format, `fun()` and `inf()` read the first object's address, and `append`
adds raw octets for a private type.

### Type identifications

Monitor direction: 1 time-tagged message, 2 time-tagged with relative time,
3 measurands I, 4 time-tagged measurands, 5 identification, 6 time
synchronization (both directions), 8 end of general interrogation,
9 measurands II, 10 generic data, 11 generic identification. Control
direction: 7 general interrogation, 20 general command, 21 generic command.
Disturbance data transfer occupies 23–31.

### Causes

1 spontaneous, 2 cyclic, 3 reset FCB, 4 reset CU, 5 start/restart, 6 power on,
7 test mode, 8 time synchronization, 9 general interrogation, 10 end of
interrogation, 11 local operation, 12 remote operation, 20 positive command
acknowledgement (and, in the control direction, general command), 21 negative
acknowledgement, 31 disturbance data, 40–44 the generic services.

### Function types and information numbers

`fun::` gives the standardized function types: `DISTANCE_PROTECTION` (128),
`OVERCURRENT_PROTECTION` (160), `TRANSFORMER_DIFF` (176), `LINE_DIFF` (192),
`GENERIC` (254), `GLOBAL` (255).

`inf::` gives the compatible-range information numbers, grouped as system
functions (`RESET_FCB`, `RESET_CU`, `START_RESTART`, `POWER_ON`), status
indications (`AUTO_RECLOSER_ACTIVE`, `PROTECTION_ACTIVE`, `LED_RESET`,
`TEST_MODE`, …), supervision (`TRIP_CIRCUIT_SUPERVISION`, `VT_FUSE_FAILURE`,
`GROUP_WARNING`, `GROUP_ALARM`, …), earth faults, fault indications
(`GENERAL_TRIP`, `TRIP_L1`, `ZONE1`, `GENERAL_START`, `BREAKER_FAILURE`, …),
auto-reclosure, and the measurand sets (`MEASURAND_I`, `MEASURAND_IV`,
`MEASURAND_IVPQ`, `MEASURAND_INVEN`, `MEASURAND_IL123VL123`).

The exact semantics are device-specific — check the relay's interoperability
document.

### Measurands

[`Measurand`] is a signed 13-bit value with OV (overflow) and ER (error) flags:

```rust
# use rs_iec60870_5::cs103::Measurand;
let m = Measurand::parse(0x4000);
let fraction = m.f64();        // -1.0 .. 1.0, the fraction of full scale
# assert_eq!(fraction, 0.5);
```

`f64()` is the fraction of **full scale**; the rated value corresponds to
1/1.2 or 1/2.4 of full scale depending on how the device is parameterised, so
converting to engineering units needs the device's rating.

### CP32Time2a

`cp32time2a` and `parse_cp32time2a` handle the 4-octet time-of-day tag. It
carries no date, so decoding takes the date from the host clock; a time of day
more than five minutes *ahead* of now is taken to belong to the previous day,
which keeps events that cross midnight in order. An invalid (IV) or short tag
decodes to `None`.

## Configuration

| Field | Range | Default | Meaning |
|-------|-------|---------|---------|
| `transport` | serial / tcp-client / tcp-server | serial | how FT1.2 frames are carried |
| `serial` | — | 8E1 at 9600 | serial port settings; 8E1 is typical |
| `tcp` | — | — | TCP address, connect timeout, optional TLS |
| `link_address` | 0–254 | 1 | the default device address; 255 is broadcast |
| `timeout_response_t1` | 1–255 s | 10 s | response timeout for confirmed frames |
| `timeout_repeat_t2` | 1–255 s, < t₁ | 5 s | timeout after the first repetition |
| `timeout_test_t3` | 1 s–48 h | 20 s | idle time before a keep-alive class 2 poll |
| `timeout_send_link_msg` | 1 ms–10 s | 200 ms | poll and transmit scheduler pacing |
| `max_send_queue_size` | > 0 | 100 | outbound ASDU queue capacity |
| `auto_init` | — | true | automatic time sync and interrogation on link activation |

The link operates in unbalanced mode only — the 103 standard defines no
balanced procedure — and the link address width is fixed at one octet
(`LINK_ADDR_SIZE`).

## Not implemented

* **Generic services** (ASDU 10, 11 and 21). The type identifications and raw
  send and receive work through `ClientHandler::asdu` and `Asdu::new` /
  `Asdu::append`, but there are no structured GIN/GDD/GID codecs.
* **Disturbance data transfer** (ASDU 23–31), the 103 equivalent of file
  transfer.
* **The secondary (device) side.** This module is a master only.

Because both this crate and go-iecp5 implement the master only, the
interoperability test drives a simulated relay
(`tests/common/relay.rs`) with each master in turn and compares the two runs.
That simulator is also a usable starting point for a device-side
implementation.
